# Сайт научного семинара ИКИ РАН

Ремейк [seminar.cosmos.ru](https://seminar.cosmos.ru): ближайшее заседание, архив докладов,
регистрация участников с заказом пропуска и панель управления для секретаря семинара.

**Статус:** этапы 0–4. Работают публичная часть (ближайшее заседание, «О семинаре», архив
с поиском и фильтрами, страница заседания, RU/EN), регистрация с уведомлениями, панель
управления и импорт архива со старого сайта. Дальше — развёртывание (этап 5).

## Стек

|          |                                   |
|----------|-----------------------------------|
| Python   | 3.13+                             |
| Django   | 6.1                               |
| БД       | PostgreSQL 16                     |
| Фронтенд | Django templates + htmx           |
| Пакеты   | uv (`pyproject.toml` + `uv.lock`) |

### Про версию Django

Проект стоит на 6.1 — не-LTS. Это осознанный выбор: в **апреле 2027 выходит 6.2 LTS**
с поддержкой до 2030, и переход на неё запланирован. Поддержка 6.1 заканчивается примерно
в конце 2027, так что апгрейд обязателен, а не опционален.

## Быстрый старт

```bash
cp .env.example .env
docker compose up -d db
uv sync
uv run manage.py migrate
uv run manage.py seed_demo
uv run manage.py createsuperuser
uv run manage.py runserver
```

`seed_demo` заливает демонстрационные заседания из прототипа, чтобы сайт сразу было
на что посмотреть. Настоящий архив приезжает [импортом со старого сайта](#импорт-архива-со-старого-сайта).

## Панель управления

Адрес — `/manage/`, `/django-admin/` 

Чтобы создать админ-пользователя: `python3 manage.py createsuperuser`

```bash
uv run manage.py setup_groups
```

Создаёт две роли под то, как устроен семинар:

| Роль                  | Может                                                                                        |
|-----------------------|----------------------------------------------------------------------------------------------|
| Секретарь семинара    | вести заседания, доклады, докладчиков, материалы; смотреть заявки и менять статусы пропусков |
| Руководитель семинара | то же плюс удаление и правка текстов сайта, включая согласие на обработку ПД                 |

Обеим ролям нужен `is_staff`. Пользователи заводятся в `/django-admin/`.

Заявки выгружаются в CSV и XLSX с учётом текущих фильтров. CSV пишется с BOM и
разделителем `;`

Докладчики в форме заседания вводятся построчно (`ФИО — должность, организация`),
а не выбираются из списка: на телефоне мультиселект по сотням людей неюзабелен,
а секретарь всё равно печатает ФИО из письма. Совпадение по ФИО переиспользует
существующую запись со всеми её данными.

Сайт — http://localhost:8000, панель — http://localhost:8000/manage/.

База в compose слушает порт **5433**. Порт меняется через `POSTGRES_PORT`.

Поднимает `db`, `web` (gunicorn), `worker` (очередь уведомлений) и `nginx` на порту 8080.

## Импорт архива со старого сайта

Архив заседаний переносится со [seminar.cosmos.ru](https://seminar.cosmos.ru) командой
`import_legacy`. Зависимости импорта в проде не нужны и ставятся отдельно:

```bash
uv sync --group legacy-import
uv run manage.py import_legacy --dry-run
uv run manage.py import_legacy
```

Сейчас со старого сайта импортируются **28 заседаний за 2023–2026 годы**: 36 докладов,
39 докладчиков и 36 PDF с аннотациями (около 6,5 МБ в `media/`). Двадцать девятый узел —
заготовка, у которой вместо темы и докладчика стоят звёздочки; она пропускается.

Команда идемпотентна: уже перенесённые узлы пропускаются, так что её можно запускать
повторно, если на старом сайте появилось новое заседание. Ключи:

|                                  |                                                |
|----------------------------------|------------------------------------------------|
| `--dry-run`                      | разобрать и показать, ничего не сохраняя       |
| `--update`                       | перенести заново поверх уже импортированного   |
| `--adopt-by-date`                | переписать заседания, заведённые на ту же дату |
| `--no-files`                     | не качать PDF, оставить ссылки на старый сайт  |
| `--save-dir` / `--from-dir`      | снять копию страниц / импортировать из копии   |
| `--topic`, `--status`, `--limit` | тематика, статус публикации, ограничение       |

### Что важно знать про эти данные

**Время берётся из текста страницы, а не из атрибута `datetime`.** Drupal обязан отдавать
в атрибуте UTC, но на старом сайте он заполнен непоследовательно: у одних узлов там
действительно UTC (`09:00Z` при показанных «12:00»), у других — московское время
с припиской «Z» (`15:00Z` при показанных «15:00»). Различить их программно нельзя, поэтому
источником правды считается то, что видит человек. Из атрибута берётся только дата,
а день недели из текста сверяется с ней — расхождение попадает в отчёт.

**Тематики на старом сайте нет вовсе** — рубрики появились только в новом макете. Поэтому
импорт складывает всё в рубрику-накопитель «Без тематики», а секретарь разбирает архив
через панель управления. Расставлять рубрики по ключевым словам хуже: неверная рубрика
в фильтре незаметна, пустая — видна сразу.

**Импорт не трогает то, чего не создавал.** Если на дату заседания в базе уже что-то есть
(а быстрый старт советует залить `seed_demo`, снятый с этого же сайта), узел пропускается
с объяснением — двойник в архиве хуже, чем недовезённое заседание. Перезапись включается
ключом `--adopt-by-date`; при ней сохраняются адрес и уже проставленная тематика.

**Пароли от трансляций не переносятся.** Поля под них нет, для прошедших заседаний они
бесполезны, а публиковать их в открытом архиве и не следовало бы. Каждый такой случай
попадает в отчёт, а не теряется молча.

Соответствие «узел старого сайта → заседание» хранится в `LegacySeminarLink` вместе
со старым адресом. Это и делает повторный запуск безопасным, и позволяет потом собрать
карту редиректов: у старого сайта заседания лежат по `/seminar/<slug>` — префикс тот же,
что у нового, а slug свой.

Для закрытого контура страницы снимаются снаружи и переносятся файлами:

```bash
uv run manage.py import_legacy --dry-run --save-dir ./snapshot
uv run manage.py import_legacy --from-dir ./snapshot --no-files
```

## Развёртывание

### Контейнеры (основной путь)

`deploy/Dockerfile` — multi-stage на базе образа uv. Статика собирается на этапе сборки,
миграции применяются в `deploy/entrypoint.sh` при старте.

Для закрытого контура образ переносится готовым:

```bash
podman save iki-seminar:latest | gzip > iki-seminar.tar.gz
# на целевой машине
gunzip -c iki-seminar.tar.gz | podman load
```

### Bare-metal (RED OS 7.3, AltLinux)

Системный `python3` в этих ОС может быть 3.9, чего Django 6.1 не примет, — поэтому Python
ставит uv, а не пакетный менеджер ОС:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
uv python install 3.13
uv sync --locked --no-dev
```

Юниты — в `deploy/systemd/`: сервис gunicorn, а также сервис и таймер воркера очереди
(раз в минуту). Резервное копирование — `deploy/backup/backup.sh`.

**Проверить на целевом сервере до установки:** версию glibc (нужна ≥ 2.17 для сборок
Python, которые тянет uv) и доступность GitHub и PyPI. Если сети нет — перенести кеш uv
и ставить с `uv sync --offline --locked`.

## Устройство

```
config/settings/     base / dev / test / prod
apps/core/           SiteSettings (singleton), базовые шаблоны, healthz
apps/seminars/       заседания, доклады, докладчики, архив
apps/registrations/  заявки участников, выгрузка
apps/staffpanel/     панель управления (только для staff)
apps/notifications/  очередь фоновых задач и уведомления
apps/legacy_import/  импорт архива со старого сайта (parser / client / importer)
deploy/              Dockerfile, nginx, systemd, бэкапы
```

### Два решения, которые стоит знать заранее

**Архив вычисляется, а не хранится.** «Автоматическое архивирование» — это не cron,
переключающий флаг, а свойство: заседание в архиве, если его дата прошла. Нет фоновой
задачи — нет рассинхронизации, гонок и забытого таймера. Публикационный статус
(`draft`/`published`/`hidden`) при этом ортогонален «прошло / не прошло».

**Очередь задач — свой бэкенд за штатным API `django.tasks`.** В Django 6.1 у `django.tasks`
есть только `dummy` и `immediate`; БД-бэкенда с воркером нет. Свой лежит в
`apps/notifications/backend.py` и реализует тот же `BaseTaskBackend`, поэтому вызовы
используют обычные `@task` и `.enqueue()`. Когда официальный БД-бэкенд появится, переход
сведётся к правке `TASKS` в настройках — бизнес-код не меняется.

При `ATOMIC_REQUESTS=True` постановка задачи попадает в транзакцию запроса: заявка на
семинар и уведомление о ней сохраняются вместе либо не сохраняются вовсе.

**Перевод контента — парами колонок, а не отдельной таблицей.** Интерфейс переводится через
gettext, содержимое — полями `*_ru` / `*_en` с откатом на русский (`apps/core/i18n.py`,
фильтр `{{ obj|tr:"title" }}`). Языка два, переводимых полей около десятка, а будущее
автозаполнение через LibreTranslate сводится к проходу по пустым `*_en`.

Отсюда правило для шаблонов: `*_ru` в разметке публичных страниц — ошибка, всегда `|tr:`.
Прямое обращение к колонке оставлено только в панели, где секретарь правит именно русский
исходник, и в письмах: они уходят из воркера, вне запроса, и всегда на русском.

Каталог интерфейса — `locale/en/LC_MESSAGES/`. Собранный `django.mo` лежит в репозитории:
ни Dockerfile, ни systemd-юнит `compilemessages` не запускают, а в slim-образе нет gettext.
Значит, после правки переводимых строк каталог надо пересобрать руками и закоммитить оба
файла:

```bash
uv run manage.py makemessages -l en --ignore=staticfiles --ignore=media
uv run manage.py compilemessages -l en --ignore=.venv
```

`--ignore=.venv` обязателен: без него `compilemessages` уходит перекомпилировать каталоги
самого Django. Если `django.mo` пропадёт, gettext молча отдаст msgid — английская версия
сайта станет русской, без единой ошибки в логах. На это есть тест
`test_english_page_translates_interface`.

**Поиск по архиву — полнотекстовый, с русской морфологией.** Заседание хранит
денормализованное поле `search_text` (тема, аннотация, доклады, докладчики на обоих языках),
по нему построен функциональный GIN-индекс `to_tsvector('russian', …)`. Поэтому запрос
«турбулентности» находит «турбулентность» — `icontains` так не умеет. Поле пересобирается
сигналами при изменении докладов и докладчиков.

## Отступления от макета

Прототип (`Семинар ИКИ РАН.dc.html`) воспроизводится как есть, кроме двух мест:

1. **Контраст.** Служебные серые в макете не проходят WCAG AA: `#858C95` даёт 3.07:1
   к фону, `#A8A093` — 2.34:1, при кегле 10–10.5px (нужно 4.5:1). В `static/css/tokens.css`
   они затемнены до `#5F6670` и `#6B6558`, минимальный кегль моно-подписей поднят до 11px.
   Оттенок сохранён.
2. **Навигация ссылками.** В прототипе пункты меню — `<button>`; здесь `<a href>`, иначе
   ломаются средний клик, «открыть в новой вкладке» и индексация архива.

## Персональные данные

Форма регистрации собирает ФИО, организацию, должность и почту, причём ФИО и организация
передаются в бюро пропусков. Это персональные данные по 152-ФЗ.

Что уже сделано:

- обязательный чекбокс согласия со ссылкой на страницу `/privacy/`; момент согласия
  сохраняется вместе с заявкой;
- IP не хранится: для ограничения частоты достаточно необратимого отпечатка
  (SHA-256 с солью из `SECRET_KEY`);
- срок хранения настраивается (по умолчанию 6 месяцев после заседания), удаление —
  команда `purge_registrations` и суточный systemd-таймер;
- заявки видны только сотрудникам, ПД не попадают в URL и логи.

**Остаётся блокером для публичного запуска:** текст согласия должен согласовать заказчик.
Пока поле `privacy_policy_text` в настройках сайта пусто, страница `/privacy/` честно
сообщает, что формулировка не утверждена, и не выдаёт себя за юридический документ.

## Антиспам

CAPTCHA нет намеренно: reCAPTCHA внешняя и несвободная, а сайт должен работать в закрытом
контуре. Вместо неё honeypot, ловушка по времени (подписанная метка рендера) и ограничение
частоты по отпечатку IP. Ни один из приёмов не мешает живому человеку и не ломает
доступность. Предел частоты — 30 попыток в час на адрес: сотрудники института приходят
из-за общего NAT, и предел рассчитан на это.
